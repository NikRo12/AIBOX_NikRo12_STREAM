# Находка: почему увеличение LMUL не ускорило кернелы — аппаратный лимит 2×128 бит/такт

## TL;DR

Увеличили LMUL с 1 до 8 (компилятор группирует больше векторных
регистров за проход, подтверждено в asm: `v1`→`v8`, `m1`→`m8`) — скорость
**не изменилась**: 10190→9782 MB/s на 1 потоке, 17971→17984 MB/s на 8
потоках (разница в пределах ±5% шума). Причина — в официальной
документации SpacemiT: у X100 всего **2 порта памяти по 128 бит/такт**,
независимо от LMUL. Количественно подтвердили через `perf stat`:
измеренный `L1-dcache-loads` для Scale = 250,098,682, предсказание по
формуле документации (500М элементов / 4 на инструкцию × 2 микро-опа) =
250,000,000 — совпадение с точностью **0.04%**. Компиляторными флагами
этот лимит не обойти — он аппаратный.


## Эксперимент

```bash
# LMUL=1 (базовый)
gcc -O3 -march=rv64gcv_zba_zbb_zbc_zbs -mabi=lp64d \
    -DSTREAM_TYPE=double stream_dynamic_tuned.c -o tuned_serial_lmul1 -lm

# LMUL=8 (явно запрошенная максимальная группировка регистров)
gcc -O3 -march=rv64gcv_zba_zbb_zbc_zbs -mabi=lp64d -mrvv-max-lmul=m8 \
    -DSTREAM_TYPE=double stream_dynamic_tuned.c -o tuned_serial_lmul8 -lm
```

### Дизассемблер подтверждает, что группировка реально произошла

```asm
; LMUL=1
vsetvli a5,a2,e64,m1,ta,ma
vle64.v v1,(a1)
vfmul.vf v1,v1,fa0
vse64.v v1,(a0)

; LMUL=8
vsetvli a5,a2,e64,m8,ta,ma    ; m8 вместо m1
vle64.v v8,(a1)                ; v8 вместо v1
vfmul.vf v8,v8,fa0
vse64.v v8,(a0)
```

При LMUL=8 на X100 (VLEN=256 бит) одна векторная инструкция обрабатывает
32 элемента `double` за проход вместо 4 при LMUL=1 (в 8 раз больше).

### Измеренные результаты — эффекта нет

| Конфигурация | 1 поток, Triad | 8 потоков, Triad |
|---|---:|---:|
| LMUL=1 (baseline) | 10190 MB/s | 17971 MB/s |
| LMUL=8 | 9782 MB/s | 17984 MB/s |

Разница — в пределах погрешности измерения (±5%), не системный эффект.
Также проверили `-funroll-loops` — компилятор вообще не развернул цикл
(ассемблер идентичен baseline), эффекта тоже нет. Дополнительно проверили
LMUL=2 (векторная запись ровно по размеру строки кэша, 64 байта) — тоже
без значимого эффекта (+4%, в пределах шума).

## Объяснение — официальная документация производителя

Официальная техническая документация SpacemiT по ядру X100 указывает:

> Векторный блок X100 поддерживает одновременную выдачу до двух
> инструкций работы с памятью и двух вычислительных инструкций за такт.
> Каждый порт обрабатывает микро-операцию в гранулярности 128 бит за
> такт — то есть инструкция с LMUL=1 (при VLEN=256 бит) физически
> выдаётся как **две** 128-битные микро-операции.

(источник: публичная документация по чипу SpacemiT K3, репозиторий
docs-chip; точную ссылку стоит зафиксировать отдельно перед финальной
сдачей отчёта — искали через веб-поиск, не имеем точного URL под рукой
на момент написания этого файла).

Это означает: даже если логически инструкция "просит" много данных сразу
(LMUL=8 — 2048 бит за раз), физически процессор всё равно режет запрос на
куски по 128 бит и обрабатывает не более двух таких кусков за такт.
Увеличение LMUL сокращает **число инструкций**, но не увеличивает
**пропускную способность порта** — а именно порт, а не число инструкций,
оказался узким местом в нашем случае.

## Количественное подтверждение через perf — точное совпадение чисел

Измерили `perf stat` с событием `L1-dcache-loads` для изолированного
Scale (1 поток, X100, WS=200MB, 25,000,000 элементов × 20 повторов =
500,000,000 обращений на чтение массива `c`):

```
L1-dcache-loads:u   250,098,682
```

**Проверка арифметикой предсказания**:
```
500,000,000 элементов / 4 элемента-на-инструкцию (VLEN=256/64=4, LMUL=1)
    = 125,000,000 векторных инструкций
125,000,000 инструкций × 2 микро-опа (по документации, 128-бит гранулярность)
    = 250,000,000 микро-опов
```

Предсказание (250,000,000) совпадает с измеренным значением
(250,098,682) с точностью **лучше 0.04%**. Для Add/Triad (читают по два
массива вместо одного) измеренное число ровно вдвое больше (500,101,695 и
500,100,127) — тоже полностью согласуется с формулой.

Это не просто "документация предполагает" — реальные счётчики
производительности с этого же железа подтверждают механизм численно.

## Вывод

Узкое место в наших кернелах — не кодогенерация цикла (LMUL, unroll), а
физическое ограничение векторного блока ядра X100 на 2 порта памяти по
128 бит за такт. Это архитектурное ограничение самого ядра, задокументированное
производителем и подтверждённое нашими собственными измерениями perf —
компиляторными флагами его обойти нельзя, для дальнейшего продвижения
нужны либо другие ядра (A100 с более широким VLEN — но там своя
проблема, см. `docs/findings/04_perf_load_store_asymmetry.md`), либо
принципиально другой подход (несколько потоков, что мы и делаем в
scaling-экспериментах).
