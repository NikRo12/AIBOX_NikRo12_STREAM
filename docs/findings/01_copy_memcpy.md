# Находка: компилятор подменяет Copy на glibc `memcpy()`

## TL;DR

Copy на графиках стабильно быстрее Scale/Add/Triad — компилятор подменяет
`c[j]=a[j]` на `memcpy()` (доказано дизассемблером: `j memcpy@plt` вместо
цикла, даже без векторизации). Отключили подмену флагом
`-fno-tree-loop-distribute-patterns`, измерили честно на WS=200MB: честный
Copy = 12454.5 MB/s, memcpy-Copy ≈ 12500 MB/s — **разницы нет**. Реальная
причина разрыва — размер рабочего набора: Copy/Scale = ×2.50 внутри L1
(34360 vs 13744 MB/s), ×2.26 внутри L2, но всего ×1.08 в RAM (12455 vs
11552 MB/s). Причина — переход compute-bound → memory-bound: внутри кэша
лишняя операция умножения у Scale заметна, в RAM прячется за ожиданием
памяти.


## Наблюдение

На всех графиках STREAM (standard и cache_sweep, любой вариант сборки, любой
тип данных) функция **Copy** систематически показывает более высокую
пропускную способность, чем Scale/Add/Triad — причём разрыв заметен даже
внутри кэша, где вычислительная нагрузка тривиальна (одно умножение
максимум) и не должна была бы иметь значения.

## Метод проверки

Извлекли кернелы STREAM в отдельные `__attribute__((noinline))` функции
(`kernel_copy`, `kernel_scale`, `kernel_add`, `kernel_triad`) — это дало
каждой функции собственное имя в скомпилированном бинарнике, за которое

можно зацепиться дизассемблером:

```bash
gcc -O3 -march=rv64gcv_zba_zbb_zbc_zbs -mabi=lp64d \
    -g -fno-omit-frame-pointer -DSTREAM_TYPE=double \
    stream_dynamic_tuned.c -o tuned_opt_serial_fp64 -lm

objdump -d --disassemble=kernel_copy tuned_opt_serial_fp64
```

## Результат

```asm
000000000000129e <kernel_copy>:
    129e: addi    sp,sp,-16
    12a0: sd      s0,0(sp)
    12a2: sd      ra,8(sp)
    12a4: addi    s0,sp,16
    12a6: blez    a2,12b6 <kernel_copy+0x18>
    12aa: ld      s0,0(sp)
    12ac: ld      ra,8(sp)
    12ae: slli    a2,a2,0x3
    12b0: addi    sp,sp,16
    12b2: j       970 <memcpy@plt>      ; <-- вот здесь
    12b6: ld      ra,8(sp)
    12b8: ld      s0,0(sp)
    12ba: addi    sp,sp,16
    12bc: ret
```

Функция `kernel_copy`, реализующая `c[j] = a[j]`, **не содержит цикла
вообще**. Вместо этого компилятор распознал паттерн поэлементного
копирования массива и заменил всю функцию прыжком на `memcpy@plt` —
вызов стандартной библиотечной функции копирования памяти из glibc.

**Важно**: это происходит **даже в сборке `novec`** (`-fno-tree-vectorize`,
автовекторизация явно запрещена). Значит, подмена на `memcpy` — это
отдельная оптимизация компилятора ("idiom recognition", распознавание
типовых паттернов кода), не связанная с флагом векторизации. Запретить
автовекторизацию — не значит запретить эту подмену.

## Почему это объясняет разрыв в скорости

`memcpy()` в glibc — это вручную оптимизированная, отдельно
протестированная функция, которая учитывает множество вещей, которые
наивный компилятор не станет генерировать сам по себе для простого цикла:
проверку выравнивания данных, выбор оптимальной ширины операций в
зависимости от размера копируемого блока, и другие low-level трюки,
накопленные годами тюнинга под конкретные семейства процессоров.

Kernel Scale/Add/Triad, для сравнения, компилятор векторизует **сам**,
без подстановки готовой библиотечной реализации — получается обычный,
"наивный" векторизованный цикл (см. `docs/findings/02_lmul_experiment.md`
про структуру этого цикла и его ограничения).

**Вывод**: сравнение "Copy быстрее остальных" — это не сравнение
"копирование быстрее, чем чтение+запись+вычисление" в общем смысле. Это
сравнение **принципиально разного кода**: одна функция — это чужой,
отдельно оптимизированный библиотечный код, три остальные — это то, что
сгенерировал автовекторизатор GCC на лету. Сопоставлять их напрямую как
"нормы производительности одного и того же уровня оптимизации" некорректно.

## Дополнительное наблюдение (побочный эффект того же механизма)

Тот же тип подмены был замечен ещё раз в другом месте — инициализация
массива нулями (`c[j] = 0.0`) была подменена компилятором на вызов
`memset()`, что видно в `perf report` (см.
`docs/findings/04_perf_load_store_asymmetry.md`, там 1.38% сэмплов
попало в `memset` из-за этой же инициализации). Это подтверждает, что
подмена стандартных паттернов на библиотечные функции — систематическое
поведение компилятора на этой платформе, а не единичный случай.

## Практическое следствие для методологии

При сравнении вариантов сборки (novec/opt_serial/omp) или типов данных
(fp64/fp32/fp16) по метрике Copy — по сути сравнивается производительность
`memcpy()` в разных условиях запуска (число потоков, размер данных), а не
эффект **наших** флагов компиляции на **наш** код. Это стоит явно
оговаривать при интерпретации графиков, где Copy — одна из четырёх линий.

## Исправление: можно отключить подмену — и результат оказался неожиданным

Подмену loop→memcpy отключает отдельный флаг `-fno-tree-loop-distribute-patterns`
(независимо от `-fno-tree-vectorize`). Проверено на x86 и на RISC-V — оба
подтверждают: без флага компилятор генерирует **собственный** векторизованный
цикл вместо вызова `memcpy@plt`.

**Важно**: `-O2` эту подмену НЕ отключает (`-ftree-loop-distribute-patterns`
включена по умолчанию начиная именно с `-O2`, не только `-O3`) — переход на
`-O2` не решает вопрос и вдобавок отключил бы автовекторизацию (она
включается только на `-O3`), что сделало бы сравнение ещё менее корректным.

Измерили честный (не-memcpy) Copy на WS=200MB, X100, 1 поток:

| Вариант Copy | Скорость |
|---|---:|
| memcpy (по умолчанию) | ~12500 MB/s |
| честный векторизованный (`-fno-tree-loop-distribute-patterns`) | 12454.5 MB/s |
| Scale (для сравнения, тоже честный) | ~11552 MB/s |

**Неожиданный результат**: честный векторизованный Copy практически не
отличается от memcpy-версии (разница <1%, в пределах шума), и разрыв с
Scale составляет всего ~8% — заметно меньше, чем можно было предположить
по разнице между Copy и остальными кернелами на графиках cache_sweep
(там на некоторых WS разрыв выглядел куда более значительным).

**Вывод требует уточнения**: на этом конкретном размере рабочего набора
(200MB, далеко за пределами кэшей) `memcpy()` не даёт значимого
преимущества над обычным компиляторным циклом — гипотеза "Copy быстрее
из-за библиотечной оптимизации" не подтверждается для этой конфигурации.
Оставшийся небольшой разрыв (~8%) между Copy и Scale, вероятно, объясняется
чем-то другим — например, тем, что Scale выполняет умножение (`vfmul.vf`)
дополнительно к load/store, что даже при тривиальной вычислительной
стоимости может занимать место в конвейере исполнения.

## Разрыв Copy vs Scale внутри кэша — проверено отдельно, объяснение найдено

Проверили тем же честным (не-memcpy) бинарником на малых WS, вписывающихся
в кэш:

| WS | Copy | Scale | Разрыв |
|---|---:|---:|---:|
| 32KB (L1) | 34360 MB/s | 13744 MB/s | **2.5×** |
| 1MB (L2) | 26574 MB/s | 11791 MB/s | **2.25×** |
| 200MB (RAM) | 12455 MB/s | 11552 MB/s | **1.08×** |

Разрыв, заметный на графиках cache_sweep, подтверждён — и он **реален**,
но проявляется именно внутри кэша, а не в RAM-зоне.

**Объяснение**: единственное структурное отличие Scale от Copy в
скомпилированном коде — одна дополнительная инструкция `vfmul.vf`
(умножение). Цикл при этом строго последовательный, без развёртки (см.
`docs/findings/02_lmul_experiment.md`) — каждая итерация ждёт: загрузка →
(умножение) → запись → переход, без перекрытия с соседними итерациями.

- **Внутри кэша** load/store занимают единицы тактов — задержка умножения
  (тоже несколько тактов, пока результат "созреет" по конвейеру) добавляет
  **значительную долю** к времени итерации → большая относительная разница.
- **В RAM** load/store занимают сотни тактов ожидания памяти — на этом
  фоне задержка умножения теряется, разрыв почти исчезает.

Это согласуется с находкой про отсутствие loop unrolling: именно из-за
отсутствия развёртки задержка вычисления не может "спрятаться" за
исполнением соседних независимых итераций, а прямо добавляется к
критическому пути каждого прохода цикла.

## Внешняя валидация: наш `memcpy`-результат в том же порядке величины, что у независимых обзоров

Независимый обзор SpacemiT K3 (CNX Software, тестирование sbc-bench,
автор Sander, инструмент tinymembench) на другом экземпляре платы измерил
`memcpy` напрямую: **6045 MB/s**. Для сравнения, тот же tinymembench-тест
на Raspberry Pi 5 дал 4870-6061 MB/s — практически тот же диапазон, что
и у K3, отсюда и вывод обзора: *"пропускная способность памяти K3
выглядит низкой, лишь немного лучше Raspberry Pi 5"*.

Наш собственный `memcpy`-based Copy на одном потоке — ~12500 MB/s, то
есть выше, чем их 6045 MB/s. Точное совпадение не ожидается (разные
размеры рабочего набора, версия ОС/ядра, настройка governor — мы
фиксировали `userspace`/2.2 ГГц, у них могли быть другие условия), но
оба числа — **одного порядка величины**, оба далеко от заявленного
пика 51.2 GB/s, и оба получены через один и тот же системный вызов
`memcpy()`. Это подтверждает: низкая пропускная способность памяти на
данной платформе — не артефакт нашей конкретной методологии измерения,
а воспроизводимая на разных стендах характеристика самого чипа K3.
