# Находка: FP16-арифметика в ~88 раз медленнее Copy — программная эмуляция вместо векторизации

## TL;DR

FP16-арифметика (Scale/Add/Triad) была в **88 раз медленнее** Copy того
же типа: 143.9 MB/s против 12739 MB/s. Дизассемблер показал причину:
компилятор эмулировал FP16 программно (`__extendhfsf2`/`__truncsfhf2` —
расширение до float, вычисление, сужение обратно на каждый элемент)
вместо векторных инструкций, потому что в `-march` не было указано
расширение `zvfh`. Добавили `zvfh` явно → компилятор сгенерировал
нативные `vle16.v`/`vfmul.vf`/`vse16.v` без единой конвертации → скорость
выросла до **12467.5 MB/s (×87 прирост)**, сравнявшись с fp32/fp64.
Причина была не в железе и не в компиляторе как таковом, а в неполной
строке march, использованной для всего проекта.


## Наблюдение

Стандартный прогон STREAM (WS=10M элементов, X100, 1 поток, `opt_serial`):

```
Function    Best Rate MB/s
Copy:           12739.0
Scale:            143.9
Add:              149.6
Triad:            146.3
```

Copy — нормальная скорость, сопоставимая с FP32/FP64. Scale/Add/Triad —
падение в **~88 раз** относительно Copy. Для FP32 и FP64 такого разрыва
между Copy и остальными кернелами близко нет (там разрыв — единицы
процентов на большом WS, см. `docs/findings/01_copy_memcpy.md`).

## Метод проверки

```bash
objdump -d test_fp16 | grep "^0.*<.*>:"
```

Список функций в бинарнике показал не только пользовательский код, но и:

```
__extendhfsf2   ; half -> float (программное расширение)
__extendhfdf2   ; half -> double
__truncdfhf2    ; double -> half (программное сужение)
__truncsfhf2    ; float -> half
```

Поиск по векторным FP16-инструкциям (`fadd.h`, `fmul.h`, `fmadd.h` —
скалярные half-precision из расширения `zfh`) дал пустой результат —
таких инструкций в бинарнике нет вообще. Единственная найденная векторная
инструкция, работающая с половинной точностью, — одна `vfmul.vf` не в
основном горячем пути.

## Объяснение

`__extendhfsf2`/`__truncsfhf2` и подобные — это функции программной
эмуляции конвертации между FP16 и более широкими типами, поставляемые
компилятором (компилятор их вставляет сам, когда не может напрямую
работать с типом в железе или не считает это оправданным). Судя по всему,
GCC 15.2.0 на данной RISC-V цели **не генерирует** нативных векторных
FP16-арифметических инструкций для Scale/Add/Triad — вместо этого на
**каждый элемент** (или каждую группу) выполняется: конвертация
half→float/double → вычисление в широком типе → конвертация обратно в
half. Каждая такая конвертация — это, по сути, вызов функции, а не одна
машинная инструкция — отсюда катастрофическое падение скорости.

Copy (`c[j]=a[j]`) не требует арифметики — компилятор либо подставляет
`memcpy()` (см. находку №1), либо копирует байты напрямую, без
конвертации типа, поэтому не задет этой проблемой.

## Почему это не аппаратное ограничение (предположительно)

В ISA-строке платы (аппаратно-программный паспорт, составленный на
раннем этапе проекта) присутствуют расширения `zvfh` (векторный
half-precision) и `zfh`/`zfhmin` (скалярный half-precision) — это
означает, что аппаратная поддержка операций с FP16, по крайней мере
частично, в железе заявлена. Проблема, судя по всему, на стороне
автовекторизатора GCC 15.2.0 — он либо не знает, как использовать `zvfh`
для этого паттерна кода, либо намеренно не делает этого на данном уровне
оптимизации. Это не подтверждено экспериментом с явными intrinsics
(отдельная, более трудоёмкая проверка, не проводилась) — формулируется
как обоснованное предположение, а не доказанный факт.

## Практическое следствие

Для этой платформы и этой версии тулчейна **FP16 непригоден** для
арифметических STREAM-подобных операций без ручного вмешательства
(intrinsics или другой компилятор/библиотека) — использование FP16 "как
есть" через обычный C-код и автовекторизацию GCC даёт катастрофически
плохой результат, несмотря на теоретическое обещание "вдвое меньше
данных — вдвое быстрее". Это стоит явно отметить в разделе отчёта про
выбор типов данных: FP16 не следует использовать на этой платформе для
подобных задач без дополнительного исследования компиляторных флагов
или ручной оптимизации.

## ИСПРАВЛЕНИЕ: проблема решена — не хватало `zvfh` в строке `-march`

После находки причины (программная эмуляция вместо векторизации)
возник вопрос: если аппаратная поддержка FP16 в ISA заявлена (`zvfh`
в паспорте платы), почему компилятор её не использует?

**Ответ**: базовое векторное расширение `v` в `-march` НЕ включает
автоматически `zvfh` — это отдельное, опциональное расширение, которое
нужно перечислить явно. Весь проект до этого момента собирался со
строкой `rv64gcv_zba_zbb_zbc_zbs` — без `zvfh`. Добавили явно:

```bash
gcc -O3 -march=rv64gcv_zvfh_zba_zbb_zbc_zbs -mabi=lp64d \
    -DSTREAM_TYPE=_Float16 stream_dynamic_tuned.c -o tuned_fp16_zvfh -lm
```

### Ассемблер — теперь нативная FP16-векторизация, без единой конвертации

```asm
vsetvli a5,a2,e16,m1,ta,ma   ; SEW=16 бит напрямую — не e32/e64!
vle16.v v1,(a1)              ; нативная векторная загрузка half
vfmul.vf v1,v1,fa0           ; нативное векторное умножение half
vse16.v v1,(a0)              ; нативная векторная запись half
```

Ни одного вызова `__extendhfsf2`/`__truncsfhf2` — компилятор работает
с 16-битными числами от начала до конца, без промежуточных конвертаций.

### Результат — аномалия устранена практически полностью

| | Scale (было, без zvfh) | Scale (стало, с zvfh) |
|---|---:|---:|
| Скорость | 143.9 MB/s | **12467.5 MB/s** |
| Кратность | — | **×87** прирост |

12467.5 MB/s — уже сопоставимо со скоростью Scale на FP64/FP32 на том же
размере рабочего набора (~11500-12500 MB/s) — то есть при правильной
строке `-march` FP16 ведёт себя нормально, никакого катастрофического
отставания.

### Обновлённый вывод

Исходный вывод "FP16 непригоден на этой платформе" был **преждевременным**
— проблема была не в железе и не в принципиальной неспособности
компилятора, а в неполной строке `-march`, которую мы использовали для
всего проекта. Это хороший пример того, как найденная и объяснённая
аномалия может оказаться не "особенностью платформы", а конкретной,
исправимой ошибкой конфигурации сборки. Рекомендация для будущих
работ на RISC-V: всегда явно проверять и указывать **все** нужные
расширения ISA в `-march`, не полагаясь на то, что базовое расширение
(`v`) включает связанные с ним опциональные части (`zvfh`, `zvfhmin`
и подобные) автоматически.

**Открытый вопрос**: весь остальной проект (fp64/fp32 замеры, cache_sweep,
scaling) был собран **без** `zvfh` в march. Поскольку `zvfh` относится
только к half-precision, на fp64/fp32 код это не должно влиять — но для
полной строгости стоило бы перепроверить хотя бы один fp64-замер с
добавленным `zvfh` в march, чтобы убедиться, что добавление этого
расширения не меняет кодогенерацию для других типов данных
(маловероятно, но не проверено явно).
