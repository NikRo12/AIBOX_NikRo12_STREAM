# Находка: асимметрия load/store в perf — 80% времени на store-инструкции, гипотеза write-allocate отклонена экспериментом

## TL;DR

`perf stat` по кернелам: Copy простаивает backend 94.07% (ждёт память),
Scale/Add/Triad простаивают **frontend** 75-79%, backend всего ~2% —
разные узкие места. `perf annotate` на Scale: **80.47%** времени — на
инструкции `vse64.v` (запись), 0.14% — на `vfmul.vf` (умножение),
9.43% — на `vle64.v` (чтение). Проверили гипотезу write-allocate (запись
= скрытое чтение старой строки кэша): изолировали "только запись" и
"только чтение", оба честно векторизованы (проверено asm). Результат:
StoreOnly = **16876 MB/s**, LoadOnly = **8537 MB/s** — запись **в 2 раза
быстрее** чтения, прямо противоположно гипотезе → **write-allocate
отклонён**. Более вероятная причина: чтение — "открытая" задержка
(процессор ждёт), запись буферизуется (store buffer, не блокирует
выполнение). Оговорка: LoadOnly-тест содержит последовательную редукцию
(сумму), что могло добавить лишнюю задержку помимо чистой асимметрии
load/store.


## Часть 1: perf stat по каждому кернелу отдельно

Изолировали каждый кернел через переменную `STREAM_KERNEL_ONLY`, чтобы
`perf stat` не усреднял все четыре разом (WS=200MB, X100, 1 поток,
`-r 5` — среднее по 5 запускам):

| | Copy | Scale | Add | Triad |
|---|---:|---:|---:|---:|
| IPC (instructions/cycle) | 0.74 | 0.61 | 0.44 | 0.45 |
| Backend простой | **94.07%** | 1.94% | 1.81% | 1.83% |
| Frontend простой | 74.43% | **75.30%** | **79.34%** | **78.55%** |
| L1-dcache-loads | 500,099,809 | 250,098,682 | 500,101,695 | 500,100,127 |
| L1-dcache-load-misses | 14,468 (0.00%) | 8,000 (0.00%) | 5,667,976 (1.13%) | 8,884,270 (1.78%) |

**Интерпретация**: у Copy (это вызов `memcpy()`, см. находку №1) backend
простаивает 94% времени — процессор буквально ждёт ответа от памяти,
классический memory-bound паттерн. У Scale/Add/Triad — наоборот, backend
почти не простаивает (~2%), а простаивает frontend (часть процессора,
готовящая следующие команды к исполнению). Это нетривиально и не имеет
пока полного объяснения — рабочая гипотеза (не доказанная строго):
связано с "развязанной" (decoupled) архитектурой блока load/store
адресации у X100, упомянутой в документации SpacemiT — векторные команды
могут уходить в отдельную очередь, и если она занята, простаивает именно
frontend, а не backend.

L1-dcache-loads по Scale/Add/Triad количественно подтверждают документацию
производителя про 2 порта × 128 бит — подробный разбор в
`docs/findings/03_lmul_experiment.md`.

## Часть 2: perf annotate — где именно концентрируется время внутри Scale

```bash
perf record -F 999 -g -o perf_scale.data -- taskset -c 0 <binary с STREAM_KERNEL_ONLY=scale>
perf annotate --stdio -i perf_scale.data kernel_scale
```

`perf report` подтвердил чистоту изоляции: 94.87% сэмплов — в
`kernel_scale`, 1.38% — в `memset` (побочный эффект инициализации
массива нулями, компилятор точно так же подменил `c[j]=0.0` на
`memset()`, как ранее `Copy` на `memcpy()` — см. находку №1).

Разбивка по инструкциям внутри `kernel_scale`:

```asm
 9.43% : vle64.v v1,(a1)      ; загрузка
 7.58% : sub     a2,a2,a5      ; служебное (счётчик цикла)
 0.14% : vfmul.vf v1,v1,fa0    ; умножение — почти бесплатно!
80.47% : vse64.v v1,(a0)       ; ЗАПИСЬ — вот где всё время
 2.11% : sh3add  a0,a5,a0      ; служебное (адресная арифметика)
 0.28% : bnez    a2,...         ; переход в начало цикла
```

**80% всего времени концентрируется на одной инструкции — векторной
записи в память.** Не на чтении, не на вычислении (умножение — 0.14%,
статистически незначимо).

## Часть 3: проверка гипотезы write-allocate — отклонена

**Гипотеза**: запись в память, которой ещё нет в кэше, требует сначала
*прочитать* всю строку кэша (даже если она будет полностью перезаписана)
— эффект называется write-allocate / read-for-ownership. Если это так,
запись должна быть **медленнее** аналогичного по объёму чтения.

### Первая попытка — методологическая ошибка

Написали изолированные кернелы "только чтение" (редукция-сумма) и
"только запись" (заполнение константой). Первый прогон показал:
LoadOnly = 5795 MB/s, StoreOnly = 16879 MB/s. Проверили дизассемблером —
`kernel_load_only` **не был векторизован** (компилятор сгенерировал
скалярный код `fld`/`fadd.d`, не `vle64.v`). Причина: сложение
чисел с плавающей запятой не строго ассоциативно, и GCC по умолчанию не
имеет права переупорядочивать сложения при редукции (это изменило бы
численный результат) — а без переупорядочивания векторизация редукции
невозможна.

**Исправлено**: добавили `-fassociative-math -fno-signed-zeros
-fno-trapping-math`, что разрешило компилятору векторизовать редукцию.
Дизассемблер подтвердил: появились `vle64.v`, `vfadd.vv`,
`vfredusum.vs` (векторная сумма).

### Честное сравнение (оба кернела векторизованы одной сборкой)

| Кернел | Скорость |
|---|---:|
| LoadOnly (векторизованный) | 8537 MB/s |
| StoreOnly (векторизованный) | **16876 MB/s** |

**Запись оказалась почти в 2 раза быстрее чтения** — прямо
противоположно тому, что предсказывала гипотеза write-allocate (там
запись должна была быть медленнее). Гипотеза write-allocate **отклонена**
на основании прямого эксперимента.

## Часть 4: альтернативная гипотеза — асимметрия задержки (exposed latency)

Более вероятное объяснение видно в самом дизассемблере `kernel_load_only`:

```asm
vle64.v  v2,(a0)          ; загрузить
vfadd.vv v1,v1,v2          ; сложить с накопителем — ЗАВИСИТ от загрузки
bnez     a1,...
```

Вычисление (`vfadd`) не может начаться, пока не завершится загрузка —
процессор вынужден **ждать** ("открытая", exposed, задержка). При записи
процессор может передать данные в **буфер записи** (store buffer) и
сразу продолжить выполнение, не дожидаясь, пока данные реально долетят
до RAM ("выстрелил и забыл"). Это согласуется с общей темой ограничения
memory-level parallelism на одном потоке: глубина буфера незавершённых
**чтений**, которые ядро может держать одновременно, — вероятно, и есть
тот самый физический потолок, а не абстрактная "нехватка параллелизма"
в целом.

## Методологическая оговорка

Тест LoadOnly считает **сумму** элементов — между итерациями есть
последовательная зависимость (каждое сложение использует результат
предыдущего). У StoreOnly такой зависимости нет вообще. Часть
двукратного разрыва может объясняться этой зависимостью в редукции, а не
исключительно природой чтения как таковой. Более чистый тест (например,
"чтение без редукции", если такой возможно сформулировать без
устранения компилятором всего цикла как бесполезного) не проводился —
отмечается как ограничение текущего эксперимента.

## Вывод

1. Copy (`memcpy`) — классический memory-bound (backend ждёт память).
2. Scale/Add/Triad — упираются в frontend, не backend; 80% времени
   Scale уходит именно на инструкцию записи.
3. Write-allocate экспериментально отклонён: запись быстрее чтения, не
   медленнее.
4. Вероятная причина — асимметрия задержки: чтение блокирует прогресс
   (exposed latency), запись буферизуется (не блокирует) — согласуется
   с общей MLP-логикой ограничения одного потока.
5. Результат имеет оговорку по чистоте методологии (зависимость в
   редукции LoadOnly).
