# Этап 1. Структура проекта STREAM (AIBOX-K3)

## Что сделано
Создана рабочая структура каталогов на плате AIBOX-K3 для проведения
исследования пропускной способности памяти (STREAM Benchmark).

## Как

mkdir -p ~/stream_bench/{src,builds/novec,builds/opt_serial,builds/omp,scripts,results/raw,results/logs,docs,sysinfo}


## Структура
- `src/` — эталонный исходник stream.c без модификаций
- `builds/novec` — сборка без автовекторизации (-fno-tree-vectorize)
- `builds/opt_serial` — оптимизированная однопоточная сборка (-O3 -march=native)
- `builds/omp` — оптимизированная многопоточная сборка (-O3 -march=native -fopenmp)
- `scripts/` — Python-скрипты автоматизации запуска и сбора результатов
- `results/raw/` — сырые CSV/JSON результаты замеров, неизменяемые вручную
- `results/logs/` — stdout/stderr каждого запуска бенчмарка
- `sysinfo/` — снимки lscpu/частот/температуры на момент замеров
- `docs/` — журнал этапов работы (этот файл и последующие)

## Почему так
Разделение raw-результатов и логов от обработанных данных нужно, чтобы
итоговые графики и таблицы строились автоматически из первичных данных
(требование задания — "исходные результаты после сохранения не должны
редактироваться вручную"). Разделение сборок по вариантам (novec/opt_serial/omp)
упрощает воспроизводимость — каждый бинарник хранит собственные объектные
файлы и флаги компиляции без конфликтов.

## Компилятор на плате
- GCC 15.2.0 — используется для всех сборок
## Дополнение: иерархия результатов по типу эксперимента

По требованию преподавателя артефакты бенчмарка должны иметь понятную
иерархию (не плоский список файлов). Структура results/ и sysinfo/
расширена подкатегориями по типу эксперимента:

results/
├── raw/{standard,cache_sweep,scaling}/
├── logs/{standard,cache_sweep,scaling}/
└── processed/ # только автогенерируемые агрегаты, не редактируется руками

sysinfo/{standard,cache_sweep,scaling}/


- `standard`   — рабочий набор >> L2, сравнение с теоретическим пиком BW
- `cache_sweep` — рабочие наборы 32KB..N MB, поиск границ L1/L2/RAM
- `scaling`    — варьирование числа потоков и CPU affinity (X100-only / A100-only / все)

## Схема run_id
Все три артефакта одного запуска (raw-результат, лог, снимок sysinfo)
связаны общим идентификатором:

    run_id = {variant}_{threads}t_{ws}_{cpuset}_run{N}_{timestamp}
    пример: omp_4t_16MB_cores0-3_run3_20260818T142315

Это гарантирует, что при разборе результатов не потребуется сопоставлять
файлы по времени модификации или угадывать соответствие — Python-скрипт
автоматизации генерирует run_id один раз на запуск и использует его как
имя файла во всех трёх директориях.
