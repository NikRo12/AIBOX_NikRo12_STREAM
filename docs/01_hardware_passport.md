# Паспорт платформы — AIBOX-K3 (ТЗ §2)

Область: только AIBOX-K3. Orange Pi 5 Plus / Banana Pi не измерялись
(см. [`08_status_vs_assignment.md`](08_status_vs_assignment.md)).

Легенда столбца «Статус»: **П** = подтверждено (документация/измерение
на железе), **Г** = гипотеза/косвенный вывод, **?** = не определено —
данных нет, сохранено как unknown, а не как предположение.

## 2. ISA и расширения

| Параметр | Значение | Статус | Источник |

### VLEN — измерено эмпирически (CSR), не только по документации

Инструмент `tools/vlen_probe/vlen_probe.c` читает CSR `vlenb` и `VLMAX`
напрямую на каждом типе ядра (инлайн-ассемблер, `vsetvli` с `rs1=x0`).

| Параметр | X100 (hart 0) | A100 (hart 8) | Статус |
|---|---:|---:|---|
| VLENB (CSR) | 32 байта | 128 байт | П — прямое измерение |
| VLEN (производное) | **256 бит** | **1024 бит** | П |
| VLMAX fp32, LMUL=1 | 8 элементов | 32 элемента | П |
| VLMAX fp64, LMUL=1 | 4 элемента | 16 элементов | П |
| VLMAX fp32, LMUL=8 | 64 элемента | 256 элементов | П |
| VLMAX fp64, LMUL=8 | 32 элемента | 128 элементов | П |

Совпадает с исходным паспортом платы (профили `zve32f`/`zve64d`) — то
есть задокументированное значение подтверждено измерением, а не принято
на веру. Сборка: `gcc -O2 -march=rv64gcv -o vlen_probe vlen_probe.c`.

## 3. Кэш-иерархия

| Параметр | X100 | A100 | Статус |
|---|---:|---:|---|
| L1D (граница по cache_sweep) | 64 КБ | 64 КБ | Г — константа `CACHE_BOUNDARIES_KB` в `scripts/run_bench.py`, откалибрована по излому графика cache_sweep, **не сверена с `lscpu -C`** |
| L2 (граница по cache_sweep) | ~3.5-4 МБ (константа в коде: 4096 КБ) | не наблюдается на измеренном диапазоне (константа в коде: 1024 КБ, но график плоский до 8 МБ) | Г — см. ниже |
| L3 | Не обнаружен | Не обнаружен | ? — в данных cache_sweep виден только один излом (L1D→L2) и переход в DRAM-плато; отдельной ступени L3 не наблюдалось ни на одном графике |
| Размер строки кэша | Не определён | Не определён | ? |

**Какие ядра разделяют кэш (X100)** — косвенный вывод, не строгий:
положение излома графика cache_sweep (переход в DRAM-плато) практически
не сдвигается при увеличении числа потоков с 1 до 8:

| Потоков | Файл графика | Излом |
|---|---|---|
| 1 (novec) | `results/processed/cache_sweep/x100/cache_sweep_novec_fp64_1t_cores0_20260818T155524.png` | ~3.2 МБ |
| 2 (omp) | `results/processed/cache_sweep/x100/cache_sweep_omp_fp64_2t_cores0-1_20260818T161236.png` | ~3.5 МБ |
| 4 (omp) | `results/processed/cache_sweep/x100/cache_sweep_omp_fp64_4t_cores0-3_20260820T113911.png` | ~3.5 МБ |
| 8 (omp) | `results/processed/cache_sweep/x100/cache_sweep_omp_fp64_8t_cores0-7_20260820T115049.png` | ~4 МБ |

Если бы L2 был приватным на ядро, суммарный вмещающийся WS при 8
потоках вырос бы кратно числу потоков (~8×) — этого не происходит.
**Вывод (Г, не подтверждён `lscpu -C`)**: L2 на кластере X100, по всей
видимости, общий на весь кластер (0-7), не приватный на ядро.

**A100 — граница L2 не проявляется**: на графике
`results/processed/cache_sweep/a100/cache_sweep_novec_fp64_1t_cores8_20260819T151255.png`
линии Copy/Scale/Add/Triad практически плоские от 256 КБ до 8 МБ — ни
малейшего перегиба у заявленной в коде границы `L2: 1024K`. Открытый
вопрос: либо арифметика на A100 ограничена самим ядром сильнее, чем
кэшем (см. [`04_perf_profiling.md`](04_perf_profiling.md)), либо
константа 1024 КБ в коде попросту неверна. Не разрешено — см.
[`07_open_questions.md`](07_open_questions.md).

### Теоретический пик пропускной способности

```
BW = MT/s × ширина_шины_бит / 8 / 1000
BW = 6400 × 64 / 8 / 1000 = 51.2 GB/s = 51200 MB/s
```

Зашито в `scripts/run_bench.py` как `THEORETICAL_PEAK_MB_S = 51200.0`,
используется для автоматического расчёта `efficiency_pct` в каждой
точке измерений. Компоненты формулы (тип памяти, MT/s, ширина шины,
число каналов) — **гипотеза** (см. таблицу выше), само число BW —
арифметическое следствие этой гипотезы, а не независимо подтверждённый
факт.

**Пиковая вычислительная производительность (FLOP/s) в этом
исследовании не рассчитывалась** — оценка compute-bound производительности
относится к GEMM-части проекта (не входит в данный репозиторий,
см. [`08_status_vs_assignment.md`](08_status_vs_assignment.md)).

## 5. Частоты CPU

| Параметр | Значение | Статус |
|---|---|---|
| Частота во время всех измерений | 2.2 ГГц, governor `userspace` (зафиксирована принудительно) | П — governor выставлялся явно перед замерами |
| Заявленная максимальная частота | 2.4 ГГц | Г — не сверена с `cpupower frequency-info` в репозитории |
| Минимальная частота | Не определена | ? |
| Вклад фиксации на 2.2 ГГц вместо 2.4 ГГц в разрыв с теорией | ~8% | Г — оценка, не изолированный эксперимент |

`scripts/run_bench.py` (`read_cpu_freqs`) снимает
`/sys/devices/system/cpu/cpuN/cpufreq/scaling_cur_freq` до и после
каждой точки измерения (`cpu_freq_before_hz`/`cpu_freq_after_hz` в raw
JSON) — то есть частота **фиксируется как факт на каждый прогон**, а не
предполагается постоянной.

## Сводка: что подтверждено, чего не хватает

| Категория | Подтверждено | Не хватает |
|---|---|---|
| Ядра/кластеры | Наличие 2×8 ядер (X100/A100), их cpuset | Модель ядер, точный список расширений на ядро |
| VLEN | Измерено эмпирически (CSR) | — |
| Кэш | Косвенно — из формы графика cache_sweep | `lscpu -C`, размер строки кэша, L3 |
| Память | Теоретическая BW посчитана | Тип/скорость/каналы — из паспорта платы, не из `dmesg`; производитель; частота DRAM в рантайме |
| Частоты CPU | Фиксируются на каждый прогон измерения | `cpupower frequency-info`, min freq |
| Тулчейн | GCC версия зафиксирована | Clang, версия ядра/ОС |

Заполнение пробелов этой таблицы — самая быстрая оставшаяся задача
перед финальной сдачей: нужен один SSH-сеанс на плату с командами
`lscpu`, `lscpu -C`, `cat /proc/cpuinfo`, `uname -a`, `clang --version`,
`cpupower frequency-info`, `find /sys/devices/system/cpu/cpu0/cache ...`,
`dmesg | grep -Ei "dram|ddr|lpddr|memory"` — данные для расчётов уже
есть, не хватает только сырых текстовых снимков команд для доказательной
базы.
