# Perf-профилирование (ТЗ §6)

Платформа: X100 (кластер AIBOX-K3), 1 поток, `taskset -c 0`, кернелы
изолированы через `STREAM_KERNEL_ONLY` в `src/STREAM_dynamic/stream_dynamic_tuned.c`.
Сборка: `-g -fno-omit-frame-pointer`, `-O3 -march=rv64gcv_zba_zbb_zbc_zbs`.
A100 профилирование не выполнено — открытый вопрос, см.
[`07_open_questions.md`](07_open_questions.md).

## 1. `perf stat -r 5` по каждому кернелу отдельно

Источники: `perf_evidence/perf_stat/{copy,scale,add,triad}.txt`.

| | Copy | Scale | Add | Triad |
|---|---:|---:|---:|---:|
| IPC (instructions/cycle) | 0.63 | 0.59 | 0.41 | 0.40 |
| Backend stalled | **93.65%** | 1.82% | 1.03% | 1.01% |
| Frontend stalled | 78.18% | **69.57%** | **85.90%** | **85.49%** |
| L1-dcache-loads | 500,100,030 | 250,097,191 | 500,098,016 | 500,097,593 |
| L1-dcache-load-misses | 15,611 (0.003%) | 7,955 (0.003%) | 12,591,722 (**2.52%**) | 11,183,831 (**2.24%**) |
| L1-dcache-stores | 563,125,883 | 313,124,172 | 313,124,433 | 313,124,323 |
| L1-dcache-store-misses | 1,858 | 1,859 | 2,722 | 2,795 |

**Cache miss rate = load-misses / loads × 100%** (формула ТЗ) — посчитана
в строке L1-dcache-load-misses выше.

**Интерпретация**:
- Copy (= `memcpy()`, см. [`06_anomalies_and_fixes.md`](06_anomalies_and_fixes.md))
  — backend простаивает 93.65% — классический memory-bound: процессор
  ждёт ответа от памяти.
- Scale/Add/Triad — противоположная картина: backend почти не простаивает
  (~1-2%), простаивает **frontend**. Не имеет полного объяснения; рабочая
  гипотеза (не доказана строго) — decoupled load/store-адресация блока
  X100 (упоминается в документации SpacemiT), см. §3.
- Add/Triad показывают заметный L1-load-miss-rate (~2.2-2.5%) в отличие
  от Copy/Scale (~0.003%) — читают по два потоковых массива вместо
  одного, больше давления на L1D.

## 2. `perf annotate` — распределение времени внутри кернела Scale

Источник: `perf_evidence/perf_record/annotate_scale.txt`
(`perf record -F 999 -g` → `perf annotate --stdio kernel_scale`).

```asm
 8.89% : vle64.v v1,(a1)        ; загрузка
 5.93% : sub     a2,a2,a5        ; счётчик цикла
 0.28% : sh3add  a1,a5,a1        ; адресная арифметика (load)
 7.35% : vfmul.vf v1,v1,fa0      ; умножение
75.84% : vse64.v v1,(a0)         ; ЗАПИСЬ — доминирует
 1.70% : sh3add  a0,a5,a0        ; адресная арифметика (store)
 0.00% : bnez    a2,...           ; переход в начало цикла
```

**75.84% времени концентрируется на одной инструкции — векторной записи
в память.** Вычисление (`vfmul.vf`, 7.35%) не бесплатно, но на порядок
дешевле записи. `perf report` (`perf_evidence/perf_record/report_scale.txt`)
подтверждает чистоту изоляции: 62.47% сэмплов — в `kernel_scale`, 8.99% —
в `memset` (побочный эффект компиляторной подмены инициализации массива
нулями — тот же механизм idiom recognition, что и Copy→`memcpy`, см.
[`06_anomalies_and_fixes.md`](06_anomalies_and_fixes.md)).

## 3. Аппаратный лимит: 2 порта памяти × 128 бит/такт (X100)

Эксперимент: увеличение LMUL с 1 до 8 (`-mrvv-max-lmul=m8`). Дизассемблер
подтверждает группировку регистров (`v1,m1` → `v8,m8`,
`perf_evidence/asm/06_kernel_scale_lmul8.txt` vs
`perf_evidence/asm/03_kernel_scale_lmul1.txt`), скорость не меняется:

| Конфигурация | 1 поток, Triad | 8 потоков, Triad |
|---|---:|---:|
| LMUL=1 | 10190 MB/s | 17971 MB/s |
| LMUL=8 | 9782 MB/s | 17984 MB/s |

Разница в пределах ±5% (шум измерения). Причина, по документации
SpacemiT (точная ссылка не зафиксирована — цитата не имеет проверенного
URL, отмечается как не до конца подтверждённый источник): у X100 всего
**2 порта памяти по 128 бит/такт**, независимо от LMUL — рост LMUL
сокращает число инструкций, но не физическую пропускную способность
порта.

**Количественная проверка через perf** (не только цитата документации):
для изолированного Scale (500,000,000 обращений на чтение массива `c`,
1 поток) измеренный `L1-dcache-loads` = 250,098,682. Предсказание по
формуле документации:

```
500,000,000 элементов / 4 элемента-на-инструкцию (VLEN=256/64=4, LMUL=1)
    = 125,000,000 векторных инструкций
125,000,000 × 2 микро-опа (128-бит гранулярность порта)
    = 250,000,000 микро-опов
```

Совпадение измерения (250,098,682) с предсказанием (250,000,000) —
точность **0.04%**. Для Add/Triad (два массива на чтение) измеренное
число ровно вдвое больше (500,101,695 и 500,100,127) — согласуется с
формулой.

## 4. Гипотеза write-allocate — отклонена экспериментом

Изолированные кернелы, оба векторизованы (подтверждено дизассемблером,
`perf_evidence/asm/08_kernel_load_only_vectorized.txt`,
`perf_evidence/asm/09_kernel_store_only_vectorized.txt`; LoadOnly
потребовал `-fassociative-math -fno-signed-zeros -fno-trapping-math`,
иначе GCC не векторизует редукцию-сумму):

| Кернел | Скорость | Источник |
|---|---:|---|
| LoadOnly (редукция-сумма) | 6549.2 MB/s | `perf_evidence/run_outputs/load_only.txt` |
| StoreOnly (заполнение константой) | 16596.2 MB/s | `perf_evidence/run_outputs/store_only.txt` |

Запись **в ~2.5 раза быстрее** чтения — прямо противоположно
предсказанию write-allocate (запись должна была быть медленнее из-за
скрытого чтения строки кэша перед записью). **Гипотеза отклонена.**

Более вероятная причина, видна в asm `kernel_load_only`: `vfadd.vv`
(накопление суммы) зависит от результата предыдущей `vle64.v` — вычисление
не может начаться, пока загрузка не завершится («открытая», exposed,
задержка). Запись уходит в буфер записи (store buffer) и не блокирует
продолжение исполнения. Согласуется с §1 (backend Scale почти не
простаивает) и с ограничением MLP на одном потоке
([`05_root_cause_analysis.md`](05_root_cause_analysis.md)).

**Методологическая оговорка**: LoadOnly считает **последовательную**
сумму элементов — часть разрыва может объясняться зависимостью между
итерациями редукции, а не исключительно асимметрией load/store как
таковой. Более чистый тест (чтение без редукции) не проводился.

## 5. Векторные инструкции RVV, найденные в горячем коде

Инструкции семейства RVV (RISC-V Vector), обнаруженные в дизассемблере
кернелов STREAM (`perf_evidence/asm/*.txt`):

| Инструкция | Назначение | Где встречается |
|---|---|---|
| `vsetvli` | настройка длины вектора (VL) и SEW/LMUL на итерацию | начало каждого векторизованного цикла |
| `vle64.v` / `vle32.v` / `vle16.v` | векторная загрузка (fp64/fp32/fp16) | Copy (честный), Scale, Add, Triad, LoadOnly |
| `vse64.v` / `vse32.v` / `vse16.v` | векторная запись | все кернелы, StoreOnly |
| `vfmul.vf` | векторное умножение на скаляр | Scale, Triad |
| `vfadd.vv` | векторное поэлементное сложение | Add, Triad, LoadOnly (редукция) |
| `vfredusum.vs` | векторная редукция-сумма | LoadOnly (после `-fassociative-math`) |

Полные дизассемблированные кернелы — `perf_evidence/asm/01`–`10`
(включая версии `lmul1`/`lmul2`/`lmul8`, честный Copy без `memcpy`,
FP16 с `zvfh`).
