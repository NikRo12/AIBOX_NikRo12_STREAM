# Аномалии: найдены, объяснены, часть — исправлена

Прямой ответ на вопрос ТЗ §9 «какие результаты реальны, а какие вызваны
артефактами измерений» — на двух конкретных примерах из этого проекта.

## FP16

### Наблюдение

Стандартный прогон (`opt_serial`, X100, 1 поток, WS=10M элементов):

```
Copy:      12739.0 MB/s
Scale:       143.9 MB/s   (в 88.5 раза медленнее Copy)
Add:         149.6 MB/s
Triad:       146.3 MB/s
```

Для fp32/fp64 такого разрыва между Copy и остальными кернелами нет
(единицы процентов на большом WS, см. ниже).

### Причина — программная эмуляция вместо векторизации

```bash
objdump -d test_fp16 | grep "^0.*<.*>:"
```

Показывает `__extendhfsf2`, `__extendhfdf2`, `__truncdfhf2`,
`__truncsfhf2` — функции программной конвертации half↔float/double.
Векторных FP16-арифметических инструкций в бинарнике нет вообще.
Причина: `-march=rv64gcv_zba_zbb_zbc_zbs`, использованный изначально во
всём проекте, **не включал** `zvfh` — векторное расширение half-precision
не входит в базовое `v` автоматически, это отдельная опция строки march.

### Исправление и результат

```bash
gcc -O3 -march=rv64gcv_zvfh_zba_zbb_zbc_zbs -mabi=lp64d \
    -DSTREAM_TYPE=_Float16 stream_dynamic_tuned.c -o tuned_fp16_zvfh -lm
```

`perf_evidence/asm/10_kernel_scale_fp16_with_zvfh.txt`:

```asm
vsetvli a5,a2,e16,m1,ta,ma   ; SEW=16 бит напрямую
vle16.v v1,(a1)              ; нативная векторная загрузка half
vfmul.vf v1,v1,fa0           ; нативное векторное умножение half
vse16.v v1,(a0)              ; нативная векторная запись half
```

Ни одного вызова конвертации.

| | Scale, без `zvfh` | Scale, с `zvfh` |
|---|---:|---:|
| Скорость | 143.9 MB/s | **12467.5 MB/s** |
| Кратность | — | **×87** |

12467.5 MB/s сопоставимо со Scale на fp64/fp32 при том же WS. Вывод:
проблема была не в железе (векторный half-precision в железе
функционален — это и есть подтверждение расширения `zvfh` в паспорте
платформы, см. [`01_hardware_passport.md`](01_hardware_passport.md)) и
не в принципиальной ограниченности компилятора, а в неполной строке
`-march`, использованной для всего проекта на момент этого замера.
Начиная с `scripts/build_dynamic.sh` (сборки после 19.08) `zvfh` включён
во все варианты по умолчанию.

### Проверка: не повлияло ли добавление `zvfh` на fp64/fp32

`builds/opt_serial/fp64` (без `zvfh`, `rv64gcv_zba_zbb_zbc_zbs`) vs
`builds_dynamic/omp/fp64` (с `zvfh`), Triad, X100, 1 поток, WS=200MB:

| Конфигурация | march | Triad |
|---|---|---:|
| `builds/opt_serial/fp64` | без `zvfh` | 10146.1 MB/s |
| `builds_dynamic/omp/fp64` | с `zvfh` | 10192.9 MB/s |

Разница 0.5% — в пределах обычного шума между прогонами (сравнимо с
разбросом 10146-10182 MB/s между тремя `opt_serial`-прогонами в один
день). Добавление `zvfh` не меняет кодогенерацию/производительность
fp64. Не formально controlled experiment (конфигурации отличаются не
только march, но и источником сборки `builds/` vs `builds_dynamic/`),
но стабильное совпадение в пределах шума достаточно для вывода «не
влияет».

## Copy = `memcpy()`, не написанный вручную цикл

### Наблюдение и причина

На всех графиках Copy стабильно выше Scale/Add/Triad, включая внутри
кэша, где вычислительная нагрузка тривиальна. Дизассемблер
(`perf_evidence/asm/01_kernel_copy_memcpy_version.txt`):

```asm
kernel_copy:
    ...
    j       970 <memcpy@plt>
    ...
```

`kernel_copy` (`c[j]=a[j]`) не содержит цикла — компилятор распознал
паттерн и подменил всю функцию на вызов glibc `memcpy()`. Происходит
**даже в `novec`** (`-fno-tree-vectorize`) — подмена не связана с флагом
векторизации, это отдельная оптимизация («idiom recognition»). `-O2` эту
подмену тоже не отключает (`-ftree-loop-distribute-patterns` включена по
умолчанию с `-O2`). Отключается отдельным флагом
`-fno-tree-loop-distribute-patterns`. Тот же механизм подменил
`c[j]=0.0` (инициализация) на `memset()` — видно в
`perf_evidence/perf_record/report_scale.txt` (8.99% сэмплов в `memset`).

### Проверка: даёт ли memcpy реальное преимущество

Честный (без подмены) векторизованный Copy vs memcpy-Copy, WS=200MB,
X100, 1 поток:

| Вариант | Скорость |
|---|---:|
| memcpy (по умолчанию) | ~12500 MB/s |
| честный векторизованный (`-fno-tree-loop-distribute-patterns`) | 12454.5 MB/s |
| Scale (для сравнения) | ~11552 MB/s |

Разница Copy честный/memcpy <1% (шум) — на этом размере WS (далеко за
пределами кэшей) `memcpy()` не даёт значимого преимущества. Оставшийся
разрыв Copy vs Scale (~8%), вероятно, из-за дополнительной инструкции
умножения (`vfmul.vf`) у Scale.

### Разрыв внутри кэша — реален, объяснён размером рабочего набора

| WS | Copy | Scale | Разрыв |
|---|---:|---:|---:|
| 32 КБ (L1) | 34360 MB/s | 13744 MB/s | 2.50× |
| 1 МБ (L2) | 26574 MB/s | 11791 MB/s | 2.25× |
| 200 МБ (RAM) | 12455 MB/s | 11552 MB/s | 1.08× |

Единственное структурное отличие Scale от Copy — одна инструкция
`vfmul.vf`; цикл не развёрнут (нет loop unrolling ни при каком LMUL, см.
[`04_perf_profiling.md`](04_perf_profiling.md)), каждая итерация ждёт
load → умножение → store последовательно. Внутри кэша load/store
занимают единицы тактов — задержка умножения заметна на их фоне; в RAM
load/store занимают сотни тактов ожидания — задержка умножения теряется.
Это переход compute-bound → memory-bound (Roofline).

### Практическое следствие

При сравнении вариантов сборки или типов данных по метрике **Copy** по
сути сравнивается `memcpy()` в разных условиях запуска, а не эффект
флагов компиляции на код проекта — учтено при интерпретации графиков в
[`03_bandwidth_results.md`](03_bandwidth_results.md).

## Вывод: не всякая аномалия — особенность платформы

FP16 (×88 медленнее) оказался исправимой ошибкой конфигурации сборки —
после фикса разница с fp32/fp64 исчезла. Copy vs Scale (до ×2.5 внутри
кэша) оказался реальным, но объяснимым эффектом Roofline-перехода, а не
браком измерения. Оба случая — прямой пример того, о чём спрашивает ТЗ
§9: не каждое расхождение с ожиданием требует менять вывод об
аппаратуре, иногда причина в методологии или конфигурации сборки, и это
нужно явно отличать.
